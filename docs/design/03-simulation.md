# 구상 시뮬레이션 결과

## 결론

같은 테스트셋 117문항에서 오케스트레이션 구성끼리는 과제 성공률이 갈리지 않았다. 검색 단계를 BM25, hybrid(BM25+dense), rerank(hybrid+reranker) 세 가지로 바꿔 돌려도 같았다. 고정 DAG와의 차이는 모두 paired bootstrap 95% 구간 안에서 0을 포함한다. 고정 DAG는 LLM을 한 번도 부르지 않았고, 단일 LLM 루프는 문항당 Haiku 약 3회를 썼다.

이 문서는 최적화가 아니라 구조 비교다. 어떤 칸(단계·경로·정책)이 있어야 하는지를 본다. 앞으로 다른 문서 종류가 들어오면 숫자는 바뀐다. 그래서 dev에 맞춘 값은 #현재 데이터에 맞춘 임시값에 따로 모았다.

차이는 문항 유형별 강약과 실패 모드에서 났다. 아래 표는 BM25 실행 기준이고, 검색 단계를 바꿨을 때 달라진 점은 #검색 단계를 바꾸면에 있다.

| 구상 | 이 시뮬레이션이 보인 것 |
|---|---|
| 코드가 짜는 계획(고정 DAG) | 관계 확장·식별자 경로를 빠뜨리지 않는다. 기권 임계값과 `trace_fix` 규칙이 실패의 대부분이다 |
| 단일 LLM 도구 루프 | 질문을 검색어로 다시 쓰고 기권을 스스로 판단해서 single·unanswerable에 강하다. 관계 확장을 자주 건너뛰어 multihop에 약하다 |
| LLM planner | 결과를 보지 못하고 계획해서 불필요한 단계가 많다. 성공률은 루프와 같다 |
| DAG + LLM 전처리 1회 | 루프의 두 강점을 호출 한 번으로 가져왔다. 프롬프트 첫 판은 의도 라벨 하나가 틀려 경로 전체가 빗나갔다(0.581) |
| 되질문 | 답 끝 한 줄 + soft 반영이 가장 안전했다. 틀린 값을 받으면 hard filter는 Hit@5를 0.66에서 0.38로 떨어뜨렸다 |

## 테스트셋

`sim/testset.jsonl`은 245문항이다. 정본에서 씨앗 레코드를 고르고, Haiku가 현장 말투 질문으로 바꿔 썼다. 정답은 정본 필드로 정했다. 유형마다 40%를 dev(기권 임계값 보정), 60%를 test(채점)로 나눴다.

| 유형 | 문항(test) | 질문 | 정답 |
|---|---|---|---|
| single | 40(24) | 현상을 말하고 유사 사례를 묻는다. 절반은 제품 이름을 넣는다 | 씨앗과 그 중복 |
| logpaste | 30(18) | 타임스탬프를 붙인 로그 한 줄 | 씨앗과 그 중복 |
| multihop | 30(18) | 원인이 추론·미상인 씨앗의 현상을 말하고 원인을 묻는다 | 중복·xref로 이어진 원인 명시 레코드 |
| fix | 30(18) | 현상을 말하고 패치·수정 버전을 묻는다 | 수정 상태 6종 |
| composite | 25(15) | 원인과 패치 여부를 한 번에 묻는다 | 씨앗 + 수정 상태 |
| aggregate | 20(12) | 조건별 건수 | 정본에서 센 건수 |
| unanswerable | 20(12) | 상용 벤더 장비·현장 운용 질문. 핵심 용어가 코퍼스에 없는 것만 남겼다 | 기권 |
| clarify | 50 | 제품·버전을 뺀 현상 질문 | 씨앗. 되질문 시뮬레이션 전용 |

정답에 손댄 것과 남은 편향은 아래와 같다.

| 항목 | 내용 |
|---|---|
| 수정 상태 검수 | 규칙으로 매긴 test 33개를 사람이 읽고 6개를 고쳤다(`gold_note` 열). 버전 표기 `19.0.0.0rc1`·`v1.1.0` 누락, "반영되지 않았다"가 다른 제안을 가리킨 경우, "정상 동작 확인" 오독이다 |
| 질문 누수 | 질문과 씨앗 제목의 글자 3-gram 겹침 중앙값 0.36, p90 0.68 |
| 관계 편향 | multihop 정답은 시스템이 확장에 쓰는 바로 그 중복·xref 관계에서 나왔다. 그래프 이득이 부풀어 있다 |
| 로그 편향 | logpaste 로그 줄은 정답 레코드 본문에서 가져왔다. 식별자 정확 일치가 유리하다 |

## 비교한 구성

모두 같은 도구 6개(`sim/engine.py`)를 쓴다. 도구는 BM25 검색, 식별자 역색인, 레코드 조회, 중복·xref 확장, `trace_fix`, 집계다. 검색 도구의 안쪽은 BM25(기본), hybrid, rerank 가운데 하나를 끼운다(#검색 단계를 바꾸면).

| 구성 | 계획 | 기권 판단 | LLM |
|---|---|---|---|
| `bm25_only` | 검색 한 번 | BM25 최고점 < τ | 없음 |
| `dag_regex` | 정규식 slot·의도 → 코드가 정한 경로 | 식별자 일치 없음 ∧ 최고점 < τ | 없음 |
| `dag_llm_slots` | 위와 같고 slot·의도만 Haiku가 15문항 묶음으로 뽑는다 | 위와 같음 | 묶음당 1회 |
| `dag_llm_front` | Haiku가 검색어·의도·slot·범위 판단을 내고 코드가 경로를 정한다 | Haiku의 `in_scope` | 문항당 1회 |
| `llm_loop` | Haiku가 도구를 한 번씩 부르며 다음 행동을 정한다(최대 6회) | Haiku | 문항당 여러 번 |
| `llm_planner` | Haiku가 결과를 보기 전에 단계 계획(JSON)을 내고 코드가 실행한다 | `dag_regex`와 같은 코드 규칙 | 문항당 1회 |

τ는 dev에서 정했다(42.6). dev의 답이 있는 문항 62개와 없는 문항 8개로, 둘의 정답률 평균이 가장 높은 값을 골랐다.

## 결과

이 절부터 #되질문까지의 수치는 BM25 실행이다. 유형별 과제 성공률이다. 성공은 유형마다 다르게 정의했다. single·logpaste는 기권하지 않고 정답이 상위 5건 안에 든 것, multihop은 정답이 상위 10건 안에 하나라도 든 것, fix는 수정 상태 일치, composite는 둘 다다.

| 구성 | single | logpaste | multihop | fix | composite | aggregate | unanswerable | 전체 | LLM 호출 | LLM 초 |
|---|---|---|---|---|---|---|---|---|---|---|
| `bm25_only` | 0.792 | 0.444 | 0.389 | 0 | 0 | 0 | 0.833 | 0.376 | 0 | 0 |
| `dag_regex` | 0.792 | 1.000 | 0.944 | 0.667 | 0.600 | 1.000 | 0.833 | **0.829** | 0 | 0 |
| `dag_llm_slots` | 0.792 | 1.000 | 0.944 | 0.667 | 0.667 | 1.000 | 0.750 | 0.829 | 0.08 | 0.9 |
| `dag_llm_front` | 0.833 | 0.944 | 0.889 | 0.667 | 0.667 | 0.750 | 1.000 | 0.821 | 1 | 5.1 |
| `llm_loop` | 0.917 | 0.778 | 0.722 | 0.667 | 0.733 | 1.000 | 0.917 | 0.812 | 2.98 | 13.8 |
| `llm_planner` | 0.750 | 0.889 | 0.833 | 0.722 | 0.733 | 1.000 | 0.833 | 0.812 | 1 | 5.6 |

`dag_regex` 대비 차이(paired bootstrap 4,000회)는 다음과 같다. `bm25_only` −0.453 [−0.538, −0.359]는 수정 상태·건수에 답하지 못해서다. `dag_llm_front` −0.009 [−0.060, 0.051], `llm_loop` −0.017 [−0.094, 0.068], `llm_planner` −0.017 [−0.068, 0.026]은 모두 0을 포함한다.

`dag_llm_slots`의 LLM 수치는 slot 묶음 9회 100초를 117문항에 나눈 값이다. LLM 초는 `claude -p` 호출 시간이라 CLI 기동이 포함된다. 실제 API 지연보다 크다.

## 계획을 누가 세우나

고정 DAG와 루프·planner는 성공률이 같았다. 실패 원인은 달랐다.

| 구성 | 실패 20~22건의 주된 원인 |
|---|---|
| `dag_regex` | 기권 임계값이 답이 있는 문항을 막음 8건(single 4), 레코드는 맞고 `trace_fix`가 상태를 틀림 5건 |
| `llm_loop` | 수정 상태 9건, multihop 5건, logpaste 4건. multihop 18문항 중 관계 확장을 부른 것은 10문항이다. 틀린 수정 상태 10개는 모두 루프가 고른 레코드에 도구가 낸 값 그대로였다 |
| `llm_planner` | 기권 임계값 8건(DAG와 같은 코드 규칙), 수정 상태 5건, 그 밖의 검색 실패 9건 |

문항당 도구 호출은 루프가 1.98회로 가장 적다. DAG는 3.14회, planner는 2.92회다. planner는 single 문항에 `trace_fix`를 19번, unanswerable 문항에 관계 확장을 8번 넣었다. 결과를 보고 멈추는 루프보다 계획이 부풀었다.

루프가 single에서 앞선 이유는 두 가지다. 질문을 검색어로 다시 써서 MRR이 0.868이다(DAG 0.681). 기권을 스스로 판단해서 답이 있는 문항을 한 번도 막지 않았다(DAG는 single 16.7%).

## LLM 전처리 한 번으로 옮기기

루프의 두 강점만 DAG 앞단 호출 한 번으로 옮긴 것이 `dag_llm_front`다. Haiku가 검색어, 의도, slot, 범위 판단을 한 번에 낸다. 둘째 판에서 single 0.833, unanswerable 1.000, 오기권 0을 얻었다.

aggregate는 0.750으로 떨어졌다. 실패 3건은 모두 record_type이다. 목록에 없는 값 "CI·빌드 이슈"를 낸 것이 2건, "oai 결함"에서 "결함"을 놓친 것이 1건이다. 출력 값을 목록과 대조하는 코드 검사가 있었으면 막혔다.

첫 판(`sim/results/dag_llm_front_v1.jsonl`)은 0.581이었다. Haiku가 "로그가 반복해서 찍힙니다"를 건수 질문으로 읽었고, 로그 타임스탬프에서 연도 2026을 뽑았다. 고정 DAG는 aggregate 의도가 켜지면 검색을 건너뛴다. 그래서 logpaste 18문항 중 14문항이 집계 숫자로 끝났다.

같은 오분류가 있어도 루프는 결과를 보고 돌아왔다. 고정 경로는 라벨 하나에 경로 전체가 걸린다. 그래서 배타적인 경로(집계)를 여는 의도는 코드 검사를 하나 더 거쳐야 한다. 예를 들어 "몇 건"류 낱말이 질문에 실제로 있어야 집계 경로를 연다.

## 기권 임계값

τ를 바꿔 가며 DAG를 다시 채점했다.

| τ | single | multihop | unanswerable | 전체 |
|---|---|---|---|---|
| 0 | 0.792 | 0.944 | 0 | 0.752 |
| 31.9 | 0.792 | 0.944 | 0.500 | 0.803 |
| 42.6(dev 보정값) | 0.792 | 0.944 | 0.833 | 0.829 |
| 53.2 | 0.667 | 0.667 | 1.000 | 0.761 |

BM25 점수 하나로는 답이 없는 문항을 다 거르면 답이 있는 문항도 막힌다. dev의 답이 없는 문항이 8개뿐이라 τ 자체도 불안정하다. LLM 범위 판단(`dag_llm_front`)은 unanswerable 1.000에 오기권 0이었다.

## slot·의도 감지

test 135문항에서 의도 집합 정확 일치는 정규식 0.881, Haiku 묶음 0.993이다. 제품 slot은 0.963 대 0.978이다. 그런데 `dag_regex`와 `dag_llm_slots`의 성공률은 0.829로 같았다. 정규식이 틀린 의도는 대개 쓸데없는 `trace_fix` 호출을 더할 뿐 답을 바꾸지 않았다.

정규식은 aggregate 필터 12개 중 2개에서 "결함 아님"을 보고 record_type "결함"까지 뽑았다. 원인 분류가 "결함 아님"인 레코드는 모두 결함 유형이라 건수는 우연히 맞았다.

## 수정 상태 도구

정답 수정 상태와 `trace_fix` 규칙이 일치하는 비율은 정본에서 27/33, 문체본(records)에서 24/33이다. 세 구성의 수정 상태 정확도가 0.667~0.8에 머문 것은 대부분 이 도구 때문이다. 루프와 planner가 틀린 수정 상태는 모두 그 구성이 고른 레코드에 도구가 낸 값과 같았다. 오케스트레이션을 바꿔서는 이 오류가 줄지 않는다.

상태 목록에도 빈칸이 있다. "고쳐졌지만 참조·버전이 없음"(예: "main branch에서 이미 고쳐졌다")이 없어서 `unknown`으로 매겼다. 1차 권고안의 `trace_fix.status`에 이 상태를 더할 필요가 있다.

## 되질문

clarify 50문항에서 정책 다섯과 가상 사용자 넷을 조합했다. 정책은 이렇다.
- 묻지 않음
- 답 끝 한 줄 + hard filter
- 답 끝 한 줄 + soft boost
- 막고 묻기
- 빠진 slot을 모두 묻기

가상 사용자는 맞는 값을 대는 사람, "모름", 무시, 틀린 값을 대는 사람이다. 묻는 조건은 상위 20건의 최다 제품 비율이 τ보다 낮을 때다. 아래는 첫 응답 Hit@5와 최종 Hit@5다.

| 정책 | 묻는 비율 | 첫 응답 | 맞는 값 | 모름·무시 | 틀린 값 |
|---|---|---|---|---|---|
| 묻지 않음 | 0 | 0.66 | 0.66 | 0.66 | 0.66 |
| 끝 한 줄 + hard, τ=0.5 | 0.46 | 0.66 | 0.72 | 0.66 | **0.38** |
| 끝 한 줄 + soft, τ=0.5 | 0.46 | 0.66 | 0.68 | 0.66 | 0.66 |
| 막고 묻기, τ=0.5 | 0.46 | **0.38** | 0.72 | 0.66 | 0.38 |
| 끝 한 줄 + hard, τ=0.7 | 0.82 | 0.66 | 0.78 | 0.66 | **0.14** |
| 끝 한 줄 + soft, τ=0.7 | 0.82 | 0.66 | 0.72 | 0.66 | 0.64 |
| 빠진 slot 모두 묻기 | 1.00 | 0 | **0.80** | 0.66 | 0.28 |

이 표에서 세 가지가 보인다.

- **틀린 값에서 soft가 버텼다.** 맞는 값을 받으면 hard filter가 soft보다 4~6pt 높다. 틀린 값을 받으면 hard는 0.38·0.14로 무너지고 soft는 0.66·0.64를 지켰다. 2차 권고안의 "직접 댄 값만 hard"는 사용자가 늘 맞는 값을 댄다는 가정에 기대고 있다.
- **막고 묻기는 얻는 것이 없다.** 최종 Hit@5는 끝 한 줄과 같고, 첫 응답만 0.66에서 0.38로 떨어진다.
- **모두 묻기는 맞는 값일 때만 가장 높다.** 0.80이다. 늘 묻는 효과와 장비군 필터 효과가 겹쳐 있어서 둘을 가르지 못했다. 그 대신 첫 응답이 늘 비고, 틀린 값에는 가장 약하다.

## 검색 단계를 바꾸면

검색 도구의 안쪽만 바꾸고 나머지는 그대로 두었다. hybrid는 BM25 상위 100건과 bge-m3 dense 상위 100건을 RRF로 합친다. rerank는 hybrid 상위 30건을 bge-reranker-v2-m3로 다시 정렬한다. 기권 τ는 모드마다 dev에서 다시 맞췄다. hybrid에서는 Haiku 루프를 돌리지 않았다.

| 구성 | BM25 | hybrid | rerank | LLM 호출 |
|---|---|---|---|---|
| 검색만 | 0.376 | 0.419 | 0.470 | 0 |
| `dag_regex` | 0.829 | 0.838 | 0.863 | 0 |
| `dag_llm_slots` | 0.829 | 0.846 | 0.863 | 0.08 |
| `dag_llm_front` | 0.821 | 0.846 | 0.821 | 1 |
| `llm_loop` | 0.812 | – | 0.812 | 약 3 |
| `llm_planner` | 0.812 | 0.829 | 0.872 | 1 |

rerank에서 `dag_regex` 대비 차이는 `llm_loop` −0.051 [−0.120, 0.017], `llm_planner` +0.009 [−0.043, 0.060], `dag_llm_front` −0.043 [−0.103, 0.009]다. 셋 다 0을 포함한다.

검색 품질이 바뀌면 그 위 칸들의 효과 크기도 바뀌었다. 그래서 효과 크기가 아니라 칸이 필요한지로 읽는다.

| 칸 | BM25 | rerank | 구조로 읽은 것 |
|---|---|---|---|
| 관계 확장 | 끄면 multihop 0.944 → 0.389 | 1.000 → 0.444 | 검색이 좋아져도 필요하다 |
| 식별자 경로 | 끄면 logpaste 1.000 → 0.444 | 1.000 → 0.611 | 줄었지만 필요하다 |
| 기권 신호 | BM25 점수 τ로 single 오기권 16.7% | reranker 점수 τ로 0%. τ를 0.5~1.25배로 흔들어도 같다 | 기권은 검색 단계가 내는 점수에 기대야 한다 |
| 루프의 single 우위 | 루프 0.917, DAG 0.792 | 둘 다 0.958 | 루프의 강점은 약한 검색을 메운 것이었다 |
| 되질문(τ=0.5, 맞는 값) | 묻는 비율 46%, Hit@5 0.66 → 0.72 | 20%, 0.92 → 0.92 | 검색이 좋아지면 물을 일과 이득이 함께 준다 |
| 틀린 값에 hard filter | 0.66 → 0.38 | 0.92 → 0.72 | soft 반영은 원래 값을 거의 지켰다(BM25·rerank 그대로, hybrid −2pt) |
| 수정 상태 | 0.60~0.73 | 0.53~0.73 | `trace_fix` 규칙에 묶여 검색과 상관없다 |

세 모드 모두에서 남은 칸은 관계 확장, 식별자 경로, 검색 점수 기반 기권, soft 반영이다. 루프와 되질문은 검색이 좋아질수록 이득이 줄었다. 이 칸들은 남기되, 켜는 조건은 고정하지 않고 데이터가 바뀔 때마다 다시 잰다.

## 현재 데이터에 맞춘 임시값

아래 값은 지금 테스트셋에 맞춰 정했거나 손으로 정했다. 새 문서 종류가 들어오면 다시 정해야 하는 값이라 결론의 근거로 쓰지 않는다.

|---|---|---|

| 제품·장비군·의도 정규식 | `sim/systems.py` `PRODUCT_WORDS` 등 | 현재 7개 제품의 용어 |

| 되질문 비율 τ 0.5·0.7 | `sim/run.py` `clarify_sim` | 두 값만 시험 |
| 수정 상태 규칙 | `sim/engine.py` `FIX_RULES` | 정본 resolution 문구 |
| bge-m3, bge-reranker-v2-m3 | `sim/dense.py` | 1차 권고안의 후보. 칸을 채운 기본값이다 |

## 다시 돌리기

레포 루트에서 아래를 차례로 돈다. LLM 응답은 `sim/runs/llm_cache/`에 프롬프트 해시로 남아 있다. 그래서 같은 코드면 새 호출 없이 같은 결과가 나온다. 결정적 부분은 `PYTHONHASHSEED`와 무관하게 같은 값을 낸다(seed 1·2·3에서 확인).

```bash
python3 -I sim/build_testset.py     # 테스트셋을 다시 만든다(캐시가 있으면 같은 문항)
PYTHONHASHSEED=0 python3 -I sim/run.py
PYTHONHASHSEED=0 python3 -I sim/ablations.py
PYTHONHASHSEED=0 python3 -I sim/make_examples.py
```

hybrid·rerank 모드는 torch와 sentence-transformers가 든 venv에서 `SIM_RETRIEVER`로 고른다. 결과는 `sim/results/<모드>/`에 따로 쌓인다. 코퍼스 임베딩(`sim/runs/emb/`, 40MB)은 레포에 없고 처음 돌릴 때 만든다. RTX 4070에서 114초 걸렸다.

```bash
uv venv --python 3.12 sim/.venv
VIRTUAL_ENV=sim/.venv uv pip install torch sentence-transformers numpy --index-url https://download.pytorch.org/whl/cu128 --extra-index-url https://pypi.org/simple
PYTHONHASHSEED=0 SIM_RETRIEVER=rerank sim/.venv/bin/python -I sim/run.py
PYTHONHASHSEED=0 SIM_RETRIEVER=hybrid SIM_SKIP=llm_loop sim/.venv/bin/python -I sim/run.py
```
