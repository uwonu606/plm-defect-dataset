# 2차 권고안 최종본: 역할 분담, planner, 되질문, 멀티모달

1차 권고안의 뼈대는 그대로 둡니다. 뼈대는 결정적 정규화기, 슬롯 기반 고정 파이프라인, MCP 도구, PostgreSQL 하나입니다. 보강의 바탕은 minimal-delta 설계안입니다. role-planner-forward 설계안에서는 안전장치와 평가 장치 다섯 가지를 가져옵니다.

role-planner-forward의 LLM planner(7~8주차)와 "갈래별 검색 답"은 지금 넣지 않습니다. LLM planner는 일정이 맞지 않습니다. 이 판단은 1차의 인력 가정을 전제로 하고, 그 가정에는 사례가 없습니다(01-graphrag-ontology.md:382). 갈래별 검색 답은 이 데이터에서 이득이 보이지 않았습니다. 다만 이 측정은 갈래별 답에 불리하게 기운 표본에서 했습니다(#4-1).

"고정 파이프라인이 단일 LLM 도구 루프보다 낫다"는 측정한 결론이 아닙니다. 가설입니다. 그래서 루프 대조군을 DAG보다 먼저 만들고, 비열등 마진을 미리 정해 판정합니다(#3).

## 0. 두 설계안 심사

점수 합계는 매기지 않습니다. 기준표가 없어서 다른 사람이 같은 점수를 다시 매길 수 없습니다. 또 (b) 기준은 #3의 MA 대조군이 검증할 질문 그 자체입니다.

| 기준 | minimal-delta | role-planner-forward |
|---|---|---|
| (a) 소규모 팀이 3~6개월에 만들고 평가로 증명할 수 있나 | 강하다. 새 런타임 LLM은 VLM 하나이고, 그것도 M2로 미뤘다. 게이트마다 비교군과 퇴로가 있다. 약점이 하나 있다. 3~4주차에 M0(시그니처 추출기, `case_artifact`, 첨부 수집기, sandbox)를 S1·S1b·S1c와 겹쳐 두었다 | 약하다. 7~8주차에 LLM planner, 막는 질문, 스크린샷 OCR, P1·C1·M1·MA 게이트를 한꺼번에 둔다. 1차 로드맵의 7~8주차에는 이미 S0·S3·S2가 있다(01-graphrag-ontology.md:389). 이 안도 스스로 "빡빡하다"고 적었다(8절 7번) |
| (b) 사용자 구상을 얼마나 살리나 | 일부만 살린다. "미리 짜는 계획"은 코드가 컴파일한 DAG로 살린다. 역할 분담은 만드는 쪽으로 옮긴다 | 더 많이 살린다. 역할 worker 여섯과 LLM planner 예외 경로를 둔다. 다만 여섯 중 넷은 결정적 worker라서 이름만 에이전트다(이 안 8절 2번) |
| (c) 지연·비용·실패 모드 | 좋다. 텍스트 경로의 LLM 호출은 기본 2회다(#2). 새 실패 지점은 첨부 전처리뿐이고, 여기에는 sandbox와 상한을 둔다. 슬롯 미감지에는 약하다 | 나쁘다. planner 1회와 수정 추적 분류 k회가 더해진다. 갈래별 검색 답은 이 데이터에서 손해였다(#4-1). 가입자 식별자 마스킹과 worker 출력 타입 고정은 이 안에만 있는 좋은 장치다 |

**통합 원칙.** 뼈대는 minimal-delta로 둡니다. role-planner-forward에서는 아래 다섯 가지를 가져옵니다.
1. **단일 LLM 도구 루프 대조군(MA).** 비교군은 대회 봇처럼 LLM 하나가 같은 도구를 도는 루프입니다(`~/bot-test/agent.py:247-275`). 사용자의 "에이전틱" 직감을 말로 반박하지 않고 평가로 확인하는 장치입니다. 최종본에서는 이 대조군을 DAG보다 먼저 만듭니다(#3).
2. **의도 커버 검사.** 감지한 의도마다 실행 노드가 있거나 "확인하지 못함" 문장이 있어야 합니다. 평가는 사람이 단 정답 의도 라벨로 합니다(#2, #8-2).
3. **worker 출력은 타입이 정해진 필드로만 넘깁니다.**
4. **가입자 식별자를 가리고 IP는 가명으로 바꿉니다.**
5. **고분고분하지 않은 시뮬레이터 페르소나 넷을 둡니다.** snapshot에 catalog·prompt·평가셋 버전을 묶는 것도 함께 가져옵니다.

**지금 넣지 않는 것**
- **7~8주차의 LLM planner.** (a) 기준으로 일정이 맞지 않습니다. 이 근거는 1차 인력 가정에 기대는데, 그 가정에는 사례가 없습니다(01-graphrag-ontology.md:382). 인력이 달라지면 이 결정도 다시 엽니다(#9).
- **"막는 slot" 개념.** 집계 축은 묻지 않고, 기본값을 쓰고 가정을 표시하면 됩니다.
- **범주형 slot의 갈래별 검색 답.** #4-1을 봅니다.

**메인 세션 예비 판단에 대한 평가**
- **"역할 분담은 만드는 쪽에서 했다."** 대회에 대해서는 맞습니다. 그런데 사용자의 구상 2는 대회가 아니라 외부 영상에서 왔을 수 있습니다. 그렇다면 이 판단은 다른 질문에 답한 것입니다. 사용자에게 영상의 어느 장면에서 인상을 받았는지 묻는 것이 가장 싸게 확인하는 방법입니다. 대회 런타임에서 코드가 맡은 범위는 좁았습니다. 문의 날짜 추출, 필수 인자 검사, 쓰기 액션의 ID 출처 검사였습니다(`agent.py:111-120`, `:204-212`). 고객이 댄 ID를 정규화하지는 않았습니다. 1차와 닮은 점은 검사를 코드에 둔 것까지입니다.
- **"빠진 slot 중 결과를 갈라놓는 slot만 묻는다."** 고쳐야 합니다. 이 갈림 규칙을 다섯 slot 모두에 걸면 질의의 96~97%에서 묻습니다. 그때 고르는 slot은 대부분 version·error인데, 질의 레코드에 버전이 있는 비율은 39~54%뿐입니다. 그래서 답을 받아도 쓸 수 없는 경우가 많습니다. 묻고 받은 값으로 hard filter를 걸면 Hit@5가 떨어집니다. title 0.680→0.537, problem1 0.560→0.493이고, short6만 0.407→0.423으로 오릅니다. 같은 값을 soft로 쓰면 0.693/0.580/0.470으로 오히려 가장 높습니다([clarify-data] 3·5절, report_neighbor_filter.txt·report_neighbor_soft.txt). 이 soft 이득은 version·error 값이 정답 쪽에서 새어 들어와 부풀었을 수 있습니다(clarify-data 한계 5번). 그래서 묻는 후보는 범주형 slot(제품/저장소, 장비군)으로 한정합니다. version·error·NF는 사용자가 주면 질의 보강(soft)에만 씁니다.

## 2. 런타임 구조

```
사용자 턴(텍스트 + 붙여넣은 로그 + 첨부)
 ├─ ① 입력 수집기 [코드]  magic bytes로 종류 판별, 크기·압축 상한, IMSI·SUPI·MSISDN·IMEI 마스킹, IP 일관 가명화
 ├─ ② 첨부 전처리 [코드, sandbox]  로그·stack 줄 추출 → zip 분배 → OCR(M1) → tshark 요약(M2)
 │      └─ ②′ VLM 캡션 worker [비전 LLM, M2]  OCR 글자가 적은 그림만. 출력 필드 고정
 ├─ ③ 정규화기 [코드] + 슬롯·의도 분류기 [작은 LLM, 다중 라벨]   ←  ①② 출력도 같은 사전으로
 ├─ ④ 계획 컴파일러 [코드]  슬롯 집합 → DAG(P0). 의도마다 커버 노드를 기록
 ├─ ⑤ 실행기 [asyncio]  같은 깊이는 병렬. 노드 6·깊이 3·시간 상한. 결과는 노드 id 순서로 합침
 │      [find_by_identifier ∥ hybrid] → rerank → [expand_related ∥ trace_fix] | aggregate | lookup_vocab
 ├─ ⑥ 되질문 판정기 [코드, 검색 뒤]  끝 한 줄 | 가정 표시 | 기권+증거 요청 | 브랜치별 상태 | 없음. 카운터 확인
 ├─ ⑦ 답 생성기 [큰 LLM]  타입이 정해진 필드만 입력. 첨부 URL·파일명 문자열은 넣지 않음
 ├─ ⑧ 근거 검증기 [코드]  인용 실재 · 구절 일치 · 의도 커버 · 단계-주제 대조
 ├─ ⑨ 대화 상태 [PostgreSQL]  slot, 출처(직접/이어받음/프로필), 카운터, 보여 준 결과, snapshot ID
 └─ ⑩ 감사 로그  snapshot ID, 슬롯, DAG, 노드별 결과, 검증 전 초안 위반, 되질문 종류·카운터 → 평가셋 후보
```

| # | 구성 요소 | 종류 | 1차 대비 | 근거 |
|---|---|---|---|---|
| ① | 입력 수집기 | 코드 | 새로 | 대회 봇에는 사진 입력 경로가 아예 없어서 사진·zip 9건을 놓쳤다(final-prep.md:76,100) |
| ② | 첨부 전처리 | 코드, sandbox | 새로 | tshark, OCR, 줄 추출처럼 결정적 도구로 된다 [attachments 6절]. 따로 두는 이유는 sandbox 권한 경계다 |
| ②′ | VLM 캡션 worker | 비전 LLM | 새로, M2 | 런타임에서 떼는 유일한 LLM worker다. 떼는 이유는 모델 종류가 다르다는 것이다 |
| ③ | 정규화기 + 슬롯·의도 분류기 | 코드 + 작은 LLM | 의도 라벨을 더함 | 1차 #B-2 |
| ④ | 계획 컴파일러 | 코드 | 1차 순서도를 코드 객체로 옮김. 범위는 6주차 MA 점검으로 정한다 | #3 |
| ⑤ | 실행기 | 코드 | 그대로 | 1차 #B-2의 상한 6회 |
| ⑥ | 되질문 판정기 | 코드 | 새로 | #4 |
| ⑦ | 답 생성기 | 큰 LLM | 입력 제한을 더함 | [role-planner 1-2] 주입 차단 |
| ⑧ | 근거 검증기 | 코드 | 넓힘 | 아래 `필수:` 항목 |
| ⑨ | 대화 상태 | PostgreSQL 테이블 | 새로 | 앞 턴 slot, 카운터, 보여 준 결과는 턴을 넘어 남아야 한다. 대회 봇도 `state/`에 원자적으로 저장했다(`agent.py:75-83`). 만료 시간을 두고 RLS를 걸며, 만료 값은 출발값으로 둔다 |
| ⑩ | 감사 로그 | 코드 | 넓힘 | 되질문·첨부·재생성 지표의 원천 |

**LLM 호출 수**
- 텍스트 경로는 기본 2회입니다. 슬롯·의도 분류 1회와 답 생성 1회입니다.
- 최대 4회까지 늘 수 있습니다. ⑧ 검증이 실패해 답을 다시 쓰면 큰 LLM이 1회 더 불립니다. `trace_fix.status`를 규칙이 `unknown`으로 내면 작은 모델 분류가 붙습니다.
- 스크린샷 경로(M2 이후)에서는 이미지마다 VLM 1회가 더해집니다.
- P0에는 planner 호출이 없습니다.
- S3의 p95는 재생성 경로를 따로 잽니다. 재생성 비율은 감사 로그 지표로 둡니다.

`trace_fix.status`는 1차 #B-2대로 규칙으로 먼저 판정합니다. 작은 모델 분류는 규칙이 `unknown`을 낼 때만 씁니다. role-planner-forward는 이 분류를 상위 k건마다 붙였는데, 그렇게 할 근거를 재지 않았습니다.

**`필수:` 단계-주제 대조를 ⑧에 더합니다.**
- 답에 패치·버전 상태가 있으면, 이번 턴에 같은 case_code로 부른 `trace_fix`가 성공했어야 합니다.
- 답에 원인별 숫자가 있으면 `aggregate`가 성공했어야 합니다.
- 어긋나면 처리는 둘 중 하나입니다. 노드 상한 안이면 빠진 노드를 1회 실행해 답을 다시 씁니다. 상한을 넘으면 그 문장을 "확인하지 못함"으로 바꿉니다.
- 근거는 대회의 `known_ids` 검사입니다(`agent.py:209-211`). 이 검사는 ID가 어디서 왔는지만 봐서, 주문을 검색한 뒤 단건 조회를 건너뛰는 실패를 막지 못했습니다(HANDOFF.md:80 [aitop-lessons]).

**`필수:` 의도 커버 검사를 ⑧에 더하고, 평가는 정답 라벨로 합니다.**
- 런타임에서는 분류기가 감지한 의도마다 답에 근거 노드가 있어야 합니다. 근거 노드가 없으면 "확인하지 못한 것: …"으로 그 의도를 이름으로 적습니다.
- 이 검사는 분류기가 놓친 의도를 보지 못합니다. 1차는 슬롯 감지 오류를 10%까지 허용합니다(01-graphrag-ontology.md:374). 그래서 평가는 사람이 단 정답 의도 라벨로 합니다(#8-2 S3).
- 직접 근거는 1차 R1입니다. 이 질문은 원인과 2.4.x 패치를 한 문장에 함께 묻습니다(01-graphrag-ontology.md:212).
- 외부 사례도 1건 있습니다. Saswata의 tau-bench 단일 에이전트 기본형은 복합 요청의 약 19%에서 요청 하나를 빠뜨렸습니다(insights.md:93). 같은 글의 다른 문장은 이 값을 "기본형 실패의 약 19%"로 적어서, 무엇을 기준으로 한 19%인지 엇갈립니다.

**`필수:` 권한은 에이전트를 나눈다고 생기지 않습니다.** 읽기 권한은 1차대로 RLS와 요청별 신원 전달이 막습니다. worker 분리가 더하는 권한 경계는 첨부 sandbox 하나입니다. 이 점을 문서에 적어 둡니다. 적지 않으면 "에이전트별 권한"을 RLS 대신으로 여길 수 있습니다 [role-planner 1-2].

**`필수:` 배포 면을 1~2주차에 정합니다.** 1차는 도구를 "MCP 서버 하나로 노출"한다고 적었습니다(01-graphrag-ontology.md:160). 사용자가 어디서 묻느냐에 따라 구조가 둘로 갈립니다.
- **엔지니어가 자기 MCP host(LLM 클라이언트)에서 쓰는 경우:** host 자체가 단일 LLM 도구 루프입니다. ⑥⑦⑧은 서버 안의 복합 도구 하나(예: `ask_defects`)로 들어가야 합니다. 원자 도구만 노출하면 host가 검증기를 건너뜁니다. 첨부도 host가 먼저 받으므로 ①②의 입력이 달라집니다.
- **자체 채팅 UI인 경우:** 그림의 구조를 그대로 씁니다. MCP는 MA 대조군과 외부 연동에만 쓰면 됩니다.

정하지 않으면 입력 수집기와 MA 대조군 설계가 둘 다 흔들립니다.

## 3. planner 정책

| 단계 | 계획을 세우는 쪽 | 모양 | 여는 때 |
|---|---|---|---|
| P0 | 코드(계획 컴파일러) | 슬롯마다 정해진 하위 그래프의 합 | 7~8주. 범위는 6주차 MA 점검으로 정한다 |
| P1 | LLM이 등록된 template 가운데 하나를 고르고 인자만 채운다. 실행 전에 코드가 검사한다 | 고정된 2~3단계 사슬. 예: `get_case → search(cause 문장) → aggregate(장비군·버전별)` | 사슬형 문항이 평가셋이나 파일럿 로그에 생길 때. 대개 소스 편입(E4·E7·E9)과 함께 온다 |
| P2 | LLM이 JSON DAG를 내고, 코드가 검증한 뒤 실행한다 | 앞 결과마다 펼치는 fan-out이나 반복 탐색 | P 게이트를 통과할 때만 |

**공통 실행 규칙(P0~P2)**
- **상한:** 노드 6개(`foreach`로 펼친 것도 셈), 깊이 3, fan-out 5입니다. 시간은 검색 경로 15초, 확장 경로 30초입니다(1차 S3).
- **코드 검사:** 도구 이름이 닫힌 목록에 있는지, 인자 타입이 맞는지, `$` 참조가 실제로 있는지, case_code가 앞 도구 출력에 나왔는지 봅니다. 어긋나면 P0로 내려갑니다. 이 검사를 LLM에 맡기지 않는 이유는 외부 사례 때문입니다. 그 사례에서 LLM 검사관이 그럴듯한 가짜 ID를 승인했습니다(insights.md:89).
- **P0 병렬 짝:** 세 짝입니다. `find_by_identifier`와 hybrid 검색, 첨부 전처리와 텍스트 정규화, `expand_related`와 `trace_fix`입니다.
- **실패 처리:** 읽기 노드는 1회 다시 돌립니다. 그래도 실패하면 그 노드에 기대는 노드만 건너뛰고, "부분 답"에 빠진 단계를 이름으로 적습니다.

**P 게이트(P2를 여는 조건).** minimal-delta #2-4를 받습니다.
- 파일럿 로그에서 "고정 경로 부족" 라벨이 10% 이상이고, 그 문항이 30개 이상이어야 합니다.
- P1 template을 먼저 더합니다. 그 뒤 남은 문항에서 P2가 과제 성공률을 15pt 이상 올리고, paired bootstrap 하한이 0보다 커야 합니다.
- 10%와 15pt는 근거 없는 출발값입니다. 1차의 Neo4j 이동 신호와 같은 형식으로 잡았습니다.

**`제안:` MA 대조군을 DAG보다 먼저 만들고, 비열등 마진으로 판정합니다.**
- **만드는 때:** 5~6주차 끝에 만듭니다. 그때는 검색과 `trace_fix` v0가 있습니다(01-graphrag-ontology.md:387-388). [추정] 루프는 수백 줄이면 된다(사례: 대회 봇의 루프와 검사가 `agent.py:195-280`, 약 85줄 안에 들어감, 1건).
- **같게 둘 것:** 두 비교군은 같은 정규화기 출력, 같은 도구, 같은 근거 검증기(⑧)를 씁니다. 오케스트레이션만 다릅니다. 루프 쪽은 큰 LLM 하나가 최대 6라운드 돕니다(`agent.py:30`).
- **6주차 점검(dev):** S0 씨앗 문항의 복합 하위셋에서 루프가 실패하는 문항 유형을 기록합니다. 루프가 아래 마진 안에 들면, 7~8주차 P0 컴파일러는 루프가 실패한 유형과 병렬 짝에만 만듭니다. 마진을 벗어나면 1차 순서도 전체를 P0로 옮깁니다.
- **S3 판정 규칙(미리 고정):**
  - 비열등 마진은 출발값으로 둡니다. 주장 지지율 −3pt, 정답 의도 기준 누락률 +3pt입니다.
  - DAG가 루프보다 품질에서 우월하면(CI 하한 > 0) DAG를 유지합니다.
  - 둘이 서로 비열등이면 p95나 토큰이 20% 이상 낮은 쪽을 고릅니다. 그 차이도 없으면 코드가 적은 쪽을 고릅니다.
  - 루프가 우월하면 고정 파이프라인 결정을 다시 엽니다.
  - 이 규칙은 1차 S1의 "단순한 쪽이 이기면 단순한 쪽"을 런타임 구조에도 거는 장치입니다.
- **검정력:** 복합 하위셋 크기는 1차 S2처럼 dev의 문항별 차이 분산으로 정합니다. 40문항은 출발값일 뿐입니다.

| 브랜치별 수정 상태 | 버전이 없고 상위 결과의 `trace_fix.status`가 브랜치마다 다르다 | 예: "main 수정됨, 2.4.x `not_backported`". 3개를 넘으면 앞 3개와 끝 한 줄 | 지금. 몇 번 켜질지와 정확도는 재지 않았다(#9) |
| 첨부 언급, 파일 없음·열리지 않음 | "첨부한 pcap 보면"만 있고 파일을 열 수 없다 | 다시 보내 달라고 하지 않는다. cause 값이나 에러 문구 한 줄만 청한다 | 지금 |
| 막는 질문(범주형 slot) | C 게이트 통과 | 한 번, 선택지 2~3개와 "모름·전체" | 나중 |

**hard filter를 거는 범위.** hard filter는 사용자가 이번 질문이나 끝 한 줄에 대한 답으로 직접 댄 범주형 값에만 겁니다. 프로필 값과 앞선 다른 질문에서 이어받은 값은 soft boost로만 씁니다. 근거는 둘입니다. 측정한 repo 필터의 "잃음 0"은 사용자가 늘 맞는 값을 댄다고 가정했습니다(branch_answer.py:46). 그리고 정답이 늘 같은 저장소라는 편향에서 나온 값입니다. hard filter를 건 뒤 최고점이 기권 임계값보다 낮으면, 필터 없는 결과를 "다른 제품의 유사 사례"로 붙입니다.

**묻지 않는 것.** 집계 축과 기간은 묻지 않습니다. 기본값(전체 기간, 장비군별)으로 답하고 첫 줄에 가정을 적습니다. version·error·NF는 사용자가 주면 soft 보강에만 씁니다. `search_cases.version_range`는 유사 사례 검색에서 hard filter로 쓰지 않습니다. `trace_fix`와 집계에만 씁니다.

### 4-3. 묻기 전에 채우는 순서와 상한

**채우는 순서.** 아래 순서로 채운 값은 묻지 않습니다. 코드가 이 순서를 검사합니다. 3·4번으로 채운 값은 위 규칙대로 soft로만 씁니다.
1. 정규화기
2. 첨부 전처리 출력
3. 같은 대화의 앞 턴 slot
4. 사용자 프로필(소속, 담당 제품)

근거는 대회 사례입니다. L-12와 R-14-b는 인입 계정을 알면서도 주문번호를 물었습니다(`심사_사진케이스_대화.md:26,479`).

**`필수:` 상한은 대화 상태(⑨)의 카운터로 코드가 셉니다.**
- 끝 한 줄은 답 하나에 하나입니다.
- 같은 slot은 대화에서 한 번만 묻습니다.
- 증거 요청은 원래 질문 하나에 한 번입니다. 증거를 받은 뒤에도 기권이면 "유사 사례 없음"과 확인한 범위만 적고 끝냅니다.

대회 R-14-b는 사진 요구에 네 턴을 쓰고 접수 없이 끝났습니다(final-prep.md:76). 원인은 둘이었습니다. 이미지를 받는 경로가 없어서 링크마다 다시 보내 달라고 했습니다. 그리고 같은 규칙이 프롬프트(`system_prompt.md:9,13`)와 장부(`merged.md:393`)에 있었지만, 질문을 세서 멈추는 코드가 없었습니다. 여기에 거절당해도 계속 미는 심사 고객이라는 대회 조건이 겹쳤습니다(final-prep.md:80). 카운터는 둘째 원인만 막습니다. 핵심 대응은 #5의 입력 경로와 위 표의 "열 수 없으면 다시 보내 달라고 하지 않는다" 행입니다.

- **적재 쪽 첨부보다 질의 쪽을 먼저 봅니다.** 표본 20건 가운데 원인 판단에 첨부가 필요했던 것은 4건입니다. 그 4건도 결론이 댓글 텍스트로 정본에 남았습니다 [attachments 3절].
- **[추정] 질의 입력은 이슈 보고와 모양이 같다**(사례: ran-core 이슈 6,087건에서 로그 붙여넣기 18.6%, 이미지 18.2%. 대리 지표 1건 [attachments]). 그래서 질의 쪽 처리를 적재 쪽보다 앞에 둡니다.
- **M0는 측정부터 합니다.** "잘린 로그가 검색을 해친다"는 아직 재지 않았습니다. 그래서 3~4주차에는 긴 로그 하위셋으로 두 색인의 Hit@5를 비교합니다. 하나는 normalize 뒤 본문 색인이고, 다른 하나는 `case_artifact` raw 원문을 chunk로 나눈 BM25 색인입니다. 차이가 있을 때만 시그니처 추출기를 만듭니다.

**`필수:` 첨부 URL이나 파일명 문자열을 답 생성기 입력에 그대로 넣지 않습니다.** 못 읽는 형식에는 명시 안내로 답합니다. 대회 시험 장치는 `image:` 줄을 글자로 흘려 넣었는데, 판정이 액션만 봐서 이 실패를 잡지 못했습니다(final-prep.md:119, `scenarios.py:44`).

**`필수:` 첨부 전처리는 신뢰하지 않는 입력으로 다룹니다.**
- 압축 해제 크기, 파일 수, 깊이에 상한을 둡니다.
- 압축 안의 파일 경로가 해제 폴더를 벗어나지 못하게 막습니다.
- tshark와 OCR은 네트워크와 DB가 끊긴 sandbox 프로세스에서, 시간 상한을 두고 돌립니다.
- 이 장치가 없으면 zip 하나로 전처리 노드가 멈추고, 1차의 6회·30초 상한이 무너집니다 [minimal-delta 4-4].

**`필수:` 가입자 식별자는 입력 단계에서 가리고, IP는 가명으로 바꿉니다.**
- IMSI·SUPI·MSISDN·IMEI는 ①에서 가립니다. LTE Attach Request에는 IMSI가 평문으로 실릴 수 있습니다. 가리지 않으면 고객망 pcap 하나가 감사 로그로 퍼집니다 [role-planner 4-3].
- IP는 요청 안에서 분석하는 동안 일관된 가명으로 바꿉니다. 같은 IP는 같은 토큰이 되고, 사설·공인·loopback·0.0.0.0 구분은 유지합니다. IP를 지우면 원인 정보가 사라지기 때문입니다. canonical의 cause·resolution에서 IP 모양 문자열은 10,000건 중 170건, CORE 3,019건 중 78건에 나옵니다. 예는 DF-CORE-2016-00007 `0.0.0.0`, DF-CORE-2018-00037 `45.45.0.0`, DF-CORE-2018-00084 `127.0.0.3`입니다. 정규식 집계라서 버전 문자열 오검출이 섞여 있고, 정밀도는 재지 않았습니다 [design-skeptic 반박].
- 원문 IP는 감사 로그와 평가셋 경계에서 지웁니다.
- 가린 결과는 시그니처 추출 앞에서 검사합니다.

**첨부 worker 출력 계약.** 출력은 `{kind, signatures[], identifiers[], cause_values[], image_text, summary(≤40줄), masked, source_span}`만 넘깁니다 [role-planner 4-3].

## 6. 만드는 쪽 역할 분담

| 역할 | 쓰는 것(단일 writer) | 읽기만 | 넘기는 것 |
|---|---|---|---|
| 소스 커넥터 owner(소스마다) | 자기 raw 파티션, staging 후보 행 | 정본, 어휘 | 1차 #A-3의 다섯 묶음 + 입력 형식 표 행 + 답 정책 규칙 목록 |
| 그래프·색인 writer(하나) | edge, 식별자 역색인, `case_artifact`, `image_text`, 임베딩 | staging | snapshot ID와 변경 노트 |
| 어휘 owner(도메인 전문가) | SKOS 어휘, 별칭 사전 | 후보 큐 | 주간 어휘 버전 |
| 평가셋 owner | 문항, 정답, 정답 의도 라벨, 시뮬레이터 페르소나, 입력 형식 표의 문항 열 | 감사 로그 후보 | 평가셋 버전. 소스·형식별 문항을 커넥터보다 먼저 만든다 |
| 런타임 owner | 도구 목록(=MCP 계약), DAG 규칙, 답 정책 원천, 되질문 규칙, MA 대조군 | snapshot | catalog 버전 |
| 배포 게이트 owner | 게이트 리포트 | 전부 | 배포 승인 |

1차 인력 가정(엔지니어 2명, 도메인 전문가 0.3~0.5명)에서는 한 사람이 여러 역할을 맡습니다. 그래도 "공유 산출물마다 writer는 하나"라는 규칙은 지킵니다.

**인계 규칙**
1. **`필수:` snapshot ID.** {data, index, vocab, catalog, prompt, 평가셋} 버전을 하나의 ID로 묶습니다. 배포는 평가 리포트의 ID와 같을 때만 통과시킵니다. 대회에서는 TC를 13:40판(367KB)으로 돌리고 14:19판(413KB)을 배포했습니다(final-prep.md:91).
2. **단일 writer.** writer가 아닌 역할은 산출물을 읽기만 합니다(HANDOFF.md:98 "장부 파일은 읽기만 한다"). writer는 바뀐 내용을 변경 노트로 알립니다(HANDOFF.md:59-75). 다른 역할이 writer에게 요청하는 형식은 대회 기록에 없으므로 새로 정합니다. 변경 노트에 "요청" 절을 둡니다.
3. **capability lint(CI).** 답 정책 규칙, template 노드, 입력 형식 표의 각 행이 실제 도구와 문항을 가리키는지 CI가 검사합니다. 예를 들어 "pcap을 보면 cause를 답한다"는 규칙은 M2 전에는 실패해야 합니다. 대회 장부의 증빙 규칙은 봇에 없던 사진 대조 능력을 전제했습니다(final-prep.md:101).
4. **제약을 근거로 방향을 바꿀 때는 측정값이나 문서 출처를 붙입니다.** 대회에서는 확인하지 않은 "17만 토큰이면 한도 초과"를 따르다가 15분과 TC 한 바퀴를 잃었습니다(회고재료.md:46).
5. **보류한 결정은 다시 열 조건과 함께 `decisions.md`에 적습니다.** 이 문서의 P·C·M 게이트가 그 형식입니다. 대회에서는 `/clear` 뒤에 사진 조건이 사라졌습니다(final-prep.md:115).
6. **LLM이 단 관계·충돌 표시는 원문 구절과 대조한 뒤에 합칩니다.** 대회에서 subagent가 단 [충돌] 2건 가운데 1건이 틀렸습니다(회고재료.md:36-39).
7. **커넥터는 `(case_code, extractor_version)` 키로 멱등하게 만듭니다.** 대상 저장소를 확인하지 못하면 멈춥니다. 대회의 `read.sh`·`send.sh`·`to_raw.py` 사고가 근거입니다(회고재료.md:28-30).
8. **Claude Code 세션으로 역할을 돌리면 세션 하나가 역할 하나를 맡고, 역할마다 HANDOFF에 절을 둡니다.** 대회 HANDOFF.md:31은 "두 세션"이라는 낡은 문장으로 남았습니다. 감독 세션은 본문(:24, :85)에만 나오고 자기 절이 없었습니다.

## 7. 프레임워크 선택

| 대상 | 판정 | 근거 |
|---|---|---|
| 오케스트레이션 | 직접 쓴 Python(asyncio) DAG 실행기 | P0는 결정적이고 병렬 짝은 셋이다. 프레임워크가 더해 주는 LLM 분기·handoff·계획 생성은 P2 전까지 쓰지 않는다 [frameworks 6] |

LlamaIndex의 `ctx.wait_for_event`와 LangGraph의 `interrupt()`는 재개할 때 앞 코드를 다시 돈다("Any code before the `wait_for_event` call must be safe to repeat.", "the runtime restarts the entire node from the beginning"). LlamaIndex에서 `InputRequiredEvent`를 내는 step과 응답을 받는 step을 나누면 다시 돌지 않는다 [frameworks 1·5] |
| LlamaIndex 전반 | 첫 버전에는 쓰지 않는다 | #1 표 |
| `llama-index-workflows` | P1·P2를 열 때 다시 검토한다 | 2.26.1, MIT, 필수 의존성 3개, OTel 지원. 대신 durable 재개는 직접 써야 하고, `collect_events` 반환 순서는 문서끼리 엇갈려 실측이 필요하다 [frameworks 1] |
| OCR | Tesseract(kor+eng)와 PaddleOCR을 M1에서 비교 | liteparse는 Tesseract를 감싼 것이고 기본 언어가 eng다. 두 도구의 버전과 라이선스는 확인하지 않았다. M1 착수 때 확인한다 |
| LangGraph | 사람 승인이 요청을 넘어 남는 쓰기 도구가 생기면 다시 본다 | `langgraph-checkpoint-postgres`가 "PostgreSQL 하나"와 맞는다. 관측성은 OTel로 보낸다 [frameworks 6-4] |
| Claude Agent SDK | 만드는 쪽에만 쓴다 | `AskUserQuestion`에는 코드가 만든 질문을 넣을 수 없다("You can't add your own questions"). 세션마다 CLI subprocess를 띄우고 외부 API 연결이 필요하다 [frameworks 5] |
| Pydantic | 계획 JSON과 worker 출력의 타입 검증 | 1차 #C의 LinkML 원천에서 MCP 계약과 노드 목록을 함께 생성한다 |
| tshark, (필요하면) Drain 계열 로그 파서 | 결정적 전처리 | 버전과 라이선스는 확인하지 않았다. M0·M2 착수 때 확인한다 |
