# PLM 결함 공개 대체 데이터셋

검색/RAG 시스템이 원본 PLM 결함 문서 규모(9,000건)에서 비슷한 사례를 제대로 찾는지 시험하는 데 쓴다. 합성 없이 공개 이슈 트래커의 실제 기록만으로 10,000건을 만든다.

## 규모

10,000건으로 정한 근거는 검색 구조가 갈리는 경계다. 시범 정본 402건은 평균 468자, 약 250 토큰이다. 1,000건이면 25만 토큰 안팎이라 긴 context에 전부 넣어도 된다. 10,000건이면 250만 토큰 안팎이라 1M context로도 다 들어가지 않아서 검색 단계가 꼭 필요하다. 비슷한 문서도 많아져서 hybrid 검색, reranker, 메타데이터 필터의 효과를 잴 수 있다.

## 구성

| 묶음 | 출처 | 정리 후 원본 | 채우는 순서 |
|---|---|---|---|
| `ran-core` | OAI, OCUDU, srsRAN, Open5GS, free5GC, Magma(2,000건 상한) | 약 7,900 | 1 |
| `adjacent-network` | OpenStack Neutron, Red Hat 네트워크 컴포넌트 | 약 9,400 | 2 |
| `adjacent-platform` | StarlingX, Red Hat 그 밖의 컴포넌트 | 약 14,800 | 3 |

앞 묶음부터 레코드로 바꾸고, 10,000건이 차면 멈춘다.

평가 질문은 300~500건이다. 현장 엔지니어가 현상을 보고 묻는 말투로 쓰고, 정답은 `cause_basis`가 `명시`인 레코드 ID다. 원인이 같고 현상이 다른 레코드는 한 묶음으로 표시해서 정답이 여럿인 질문을 만든다.

## 파일

| 파일 | 내용 |
|---|---|
| `dataset/records.jsonl`, `.csv` | 검색 대상. 작성자 문체·오타가 들어간 버전 |
| `dataset/canonical.jsonl`, `.csv` | 같은 `case_code`의 정본. 평가 정답과 사실 대조에 쓴다 |
| `dataset/stats.json` | 분포 집계 |

CSV는 Excel에서 바로 열리게 UTF-8 BOM으로 쓴다. 다시 만들려면 `python3 -I tools/assemble.py`를 돌린다. `duplicate_of_case`는 중복 원본이 데이터셋 안에 있을 때만 채워진다.

## 레코드 필드

| 필드 | 값 | 비고 |
|---|---|---|
| `case_code` | `DF-<장비군>-<연도>-<5자리>` | 원본 PLM 번호 체계를 흉내 내지 않는 중립 형식 |
| `record_type` | `결함`, `CI·빌드`, `기능 요청` | |
| `title` | 한 줄 요약 | |
| `equipment` | 아래 장비군 표의 값 하나 | |
| `location` | 기능·모듈, 인터페이스·프로토콜, SW 버전 | 예: `SMF / Nsmf_PDUSession / v2.7.7` |
| `problem` | 관찰된 현상, 재현 조건. 기능 요청이면 요청 배경 | 로그 한두 줄은 원문 그대로 |
| `cause` | 근본 원인 | 기능 요청이거나 미상이면 비움 |
| `cause_basis` | `명시`, `추론`, `미상`, `해당 없음` | 아래 판정 기준 |
| `cause_class` | 아래 원인 분류 표의 값 하나 | 기능 요청이거나 미상이면 비움 |
| `resolution` | 조치 내용, 수정 버전 또는 PR | 해결 기록이 없으면 닫힌 사유 |
| `origin` | 위 구성 표의 묶음 이름 | |
| `duplicate_of` | 중복 판정된 원본의 `source_id` | 중복이 아니면 비움 |
| `source_url`, `source_license` | 원본 위치와 라이선스 | |

사용법 문의와 내용이 없는 이슈는 뺀다. 제목과 본문이 서로 다른 문제를 가리키는 원본도 뺀다. 중복으로 닫힌 이슈는 남기고 `duplicate_of`에 원본을 적는다. 실제 PLM에도 같은 결함이 여러 번 등록되고, 평가에서 원인이 같은 레코드 묶음을 만드는 재료가 된다.

## cause_basis 판정

| 값 | 조건 |
|---|---|
| `명시` | 보고자·메인테이너·PR 설명이 원인을 단정하는 문장으로 적었다 |
| `추론` | 수정 내용에서 원인을 거꾸로 끌어냈거나, 원문이 `probably`처럼 단정하지 않았다 |
| `미상` | 결함·CI·빌드인데 원인 근거가 없다. stack trace에 위치만 보이는 경우도 여기다 |
| `해당 없음` | 기능 요청 |

## 장비군

| 값 | 범위 |
|---|---|
| `RAN-CU` | gNB-CU, eNB 상위 계층(RRC, PDCP, NGAP, F1AP, E1AP) |
| `RAN-DU` | gNB-DU, PHY·MAC·RLC, 스케줄러, fronthaul |
| `UE` | 단말 소프트웨어, UE 시뮬레이터 |
| `CORE` | 5GC(AMF, SMF, UPF, NRF 등), EPC(MME, SGW, PGW) |
| `OAM` | EMS, 설정·모니터링, NETCONF/YANG, 관리 SW |
| `PLATFORM` | vRAN·클라우드 플랫폼, 커널, NIC 드라이버, 가상화, 빌드·CI 인프라, 문서 사이트 |

제품 구성 요소의 빌드·테스트 실패는 그 구성 요소의 장비군을 따른다(예: MME 링크 오류는 `CORE`). CI 인프라 자체의 문제만 `PLATFORM`이다.

## 원인 분류

| 값 | 뜻 |
|---|---|
| `프로토콜 처리` | 메시지·IE 인코딩/디코딩, 필수 IE 누락 처리 |
| `상태 관리` | FSM 전이 오류, 세션·컨텍스트 정리 누락 |
| `입력 검증` | 범위·형식 검사 누락으로 assert나 crash |
| `자원 관리` | 메모리·핸들 누수, 해제 후 사용, 풀 고갈 |
| `동시성` | 경합, 교착, 순서 의존 |
| `규격 미준수` | 3GPP·O-RAN 절차와 다른 동작 |
| `연동` | 타 벤더 장비·NF와의 상호운용 |
| `설정` | 기본값 오류, 설정 파싱, 문서와 다른 동작 |
| `성능·타이밍` | 처리 지연, 타이머, 실시간 마감 위반 |
| `플랫폼` | OS, 드라이버, 하드웨어 가속기, 설치 |
| `빌드·의존성` | 컴파일 실패, 패키지 버전, 외부 저장소 |
| `테스트` | 테스트 코드 결함, 불안정한 테스트, 임계값 |
| `구현 오류` | 위 분류에 들지 않는 코드 결함 |
| `결함 아님` | 조사 결과 정상 동작이거나 미지원 기능으로 판정됐다 |

## 용어집

설명은 한국어로 쓰고 아래 용어는 영어로 둔다. 표에 없는 용어는 샘플 확인 때 정한다.

| 영어로 둠 | 한국어로 씀 |
|---|---|
| gNB, CU, DU, UE, AMF, SMF, UPF, MME | handover → 핸드오버 |
| RRC, NGAP, F1AP, PFCP, GTP-U, SCTP | crash → 비정상 종료(crash) |
| PDU session, IE, SBI, FSM | assert 실패 → assert 실패 |
| attach, registration, paging | memory leak → 메모리 누수 |
| 로그·명령·설정 키 원문 | workaround → 우회 방법 |
