# 해결책 축 2단계: `r.unresolved` 해결되지 않음 아래 고르기

이 레코드는 1단계에서 `r.unresolved`로 정해졌다. 이제 그 아래 노드 하나를 고른다.

## 할 일

1. 아래 '고르는 규칙'이 있으면 그 순서를 따른다. 없으면 정의·포함 기준이 가장 잘 맞는 노드를 고른다.
2. 더 아래 노드(세분류)가 있으면 거기까지 내려간다. 세분류를 가를 근거가 없으면 그 위 노드에서 멈춘다.
3. 하위를 가를 근거가 없으면 `r.unresolved` 그대로 답한다.
4. 고른 노드의 포함 기준에 맞는 구절을 레코드 원문에서 그대로 복사해 evidence에 넣는다.

완료 기준: 레코드마다 `label`이 아래 목록 안의 값이고, `evidence`가 원문에 글자 그대로 있는 구절이다.

## 하위 노드

### `r.unresolved.pending` 반영 대기(예정·수정안) (Fix pending: planned or proposed)

- 표준 대응: Launchpad Confirmed·Triaged·In Progress, Bugzilla ASSIGNED, OpenVEX status under_investigation·affected(조치 예정, 이번 조사에서 원문 미확인)
- 정의: 제품을 맡은 쪽이 고치거나 구현하겠다고 했거나, 누군가 구체적 수정안(patch, review, PR, 고칠 코드 줄)을 냈지만, 반영됐다는 기록이 없다.
- 포함: '다음 release에서 고치겠다', 지원하고 싶지만 시점 미정, RFE 승인 라벨만 있음, '살펴보겠다', review·PR 시작만 있음, 보고자의 수정 PR, 시험용 patch 제공 뒤 결과 없음, 보고자의 local 수정 제시, 수정안이 올라왔다가 abandon됨.
- 이웃과 가르기: merge·수정 버전·수정 내용을 적은 연결 PR이 있으면 r.change. 보고자가 제품이 어떻게 동작해야 하는지만 적었고 patch·PR·고칠 코드 줄이 없으면 _none. 재현용 PoC·branch는 수정안이 아니다. 제품이 아니라 사용자 설정을 바꾸라는 안내면 r.field.adjust. 하지 않겠다고 했으면 r.verdict.decline.

### `r.unresolved.abandoned` 해결 없이 종결 (Closed without resolution)

- 표준 대응: Bugzilla WORKSFORME·INCOMPLETE, Jira Cannot reproduce, Launchpad Expired·Incomplete, ServiceNow 'Resolved - No response from caller', GitHub not_planned 가운데 stale 종료
- 정의: 조치도 결함 판정도 없이, 활동 중단·정보 부족·재현 불가·재발 없음·대상 소멸을 이유로 닫혔거나 닫을 대상으로 표시됐다.
- 포함: stale bot 자동 종료, 'ToClose' 류 정리 표시, 재현 PoC만 붙고 정리 라벨이 붙음, 정보 부족·재현 불가로 닫음, log 만료와 최근 안정을 이유로 닫음, release EOL 일괄 종료, 더 쓰지 않는 대상이라 닫음, 보고자가 내용 없이 닫음.
- 이웃과 가르기: 닫혔다거나 닫을 대상이라는 사실이 전혀 적혀 있지 않으면 _none. 책임자가 이유를 들어 고치지 않기로 했으면 r.verdict.decline. 고치겠다는 약속이나 수정안이 있으면 주 라벨 r.unresolved.pending, 보조 라벨 이 노드. 다른 사람이 남긴 구체적 조치가 있으면 확인되지 않았어도 주 라벨 r.field, 보조 라벨 이 노드. 상태가 스스로 해소됐다고 적혔으면(알람 자동 해제 등) r.field.recover.

## 출력

`label`은 `r.unresolved`, `r.unresolved.pending`, `r.unresolved.abandoned` 가운데 하나다. JSON 객체 하나만 낸다.

```json
{"results": [{"id": "<레코드 id>", "label": "<라벨>", "evidence": "<원문 구절>"}]}
```
