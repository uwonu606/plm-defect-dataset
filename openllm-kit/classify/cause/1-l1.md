# 원인 축 1단계: 대분류 고르기

축의 질문은 "근본 원인. 결함이 어떤 종류의 요소에 있었나."이다. 근거는 레코드 유형, 원인 서술, 해결 서술에서만 찾는다.

## 할 일

1. 레코드를 읽는다.
2. 아래 질문을 Q1부터 차례로 묻고, 처음 "예"가 나온 질문에서 멈춘다. 그 질문의 라벨이 답이다.
3. 멈춘 질문에 "예"라고 답하게 한 구절을 레코드 원문에서 그대로 복사해 evidence에 넣는다.

레코드 유형이 '기능 요청'이면 코드가 이미 _na로 정했으므로 이 문서까지 오지 않는다. Q1·Q2·Q3·Q4의 순서는 원천(taxonomy/cause.json 루트)이 정한 우선순위다. Q5 이후의 순서는 이 키트가 정했다. 나머지를 받는 c.code를 마지막에 둔 것이다.

완료 기준: 레코드마다 `label`이 아래 라벨 목록 안의 값이고, `stop`이 멈춘 질문 번호(어느 질문에도 "예"가 없어 마지막 안내로 끝났으면 0)이고, `evidence`가 원문에 글자 그대로 있는 구절이다.

## 질문

| Q | 질문 | "예"이면 |
|---|---|---|
| 1 | 결함이 아니라고 판정됐나(설계대로, 미지원, 분석 도구 오탐, 보고자의 규격·코드 오독)? | `_na` |
| 2 | 원인 서술과 해결 서술 어디에도 무엇이 어떻게 틀렸는지(메커니즘)가 없나? '고쳤다', 'PR #N', '최신 버전에서 해결', '시험을 끔'뿐이면 예. 원인을 단정한 문장이 있으면 짧아도 아니오. | `_none` |
| 3 | 함께 쓰는 외부 구성요소(우리 레포 밖의 library·kernel module·toolchain·연동 시스템)가 의도적으로 바뀌었거나(새 버전의 API·기본값·동작 변경), 선언·설치된 버전이 맞지 않거나 빠졌나? 고친 곳이 시험 코드여도 예. 외부 구성요소는 그대로인데 우리가 잘못 썼거나, 외부 구성요소 자체의 bug거나, 우리 코드 안의 모듈 연결이 빠졌으면 아니오. | `c.supply` (하위: 빌드·패키징·CI 정의 오류, 의존 구성요소 변경·버전 부적합) |
| 4 | 결함이 시험 자산(test case, fixture, 시험 데이터, 판정 기준, 시험 job 구성) 안에 있나? | `c.test` |
| 5 | 제품과 운용 조직이 통제하지 않는 외부 사건·조건(정전, 물리 손상, 공격, 외부 서비스 장애)이 원인인가? | `c.env` (하위: 전원·설비 이상, 외부 물리 사건·전파 조건, 악의적 공격, 외부 서비스·기반 장애) |
| 6 | HW 요소(장비·보드·부품·회로·FPGA 논리)의 설계나 물리 상태가 원인인가? | `c.hw` (하위: HW 설계 결함, HW 고장·제조 불량) |
| 7 | 사람이 수행한 작업 절차나 망·시스템의 구성·용량 설계가 원인인가? | `c.operation` (하위: 작업 절차 오류, 구성·용량 설계 오류) |
| 8 | 코드는 맞고 설정 값·기본값·정책 파일·가입자·망 데이터·문서 내용이 틀렸거나 빠졌나? | `c.content` (하위: 설정·데이터 값 오류, 문서·안내 오류) |
| 9 | 빌드 스크립트·패키지 manifest·CI pipeline처럼 산출물을 만드는 정의가 틀렸나? | `c.supply` (하위: 빌드·패키징·CI 정의 오류, 의존 구성요소 변경·버전 부적합) |
| 10 | SW·FW 소스 코드가 의도·요구·계약과 다르게 작성됐나? 외부 library·kernel의 bug도 예. | `c.code` (하위: 처리 논리 오류, 검사·오류 처리 결함, 상태·수명주기 관리 오류, 동시성·실행 순서 오류, 자원·성능 결함, 구성요소 계약 불일치, 표현·인코딩 오류) |

Q3~Q10 어디에도 "예"가 없고 메커니즘은 적혀 있으면 `_other`.

## 대분류 정의

- `c.code` 소프트웨어 결함 (Software defect): SW·FW의 소스 코드가 의도·요구·계약과 다르게 작성되어 증상을 냈다. 제품 코드든 가져다 쓴 library·kernel·상대 장비의 SW든 같다.
- `c.hw` 하드웨어 결함 (Hardware defect): 장비·보드·부품·모듈 같은 HW 요소의 설계나 물리 상태가 원인이다. 자사 제품이든 공급사 부품이든 같다.
- `c.content` 설정·데이터·문서 내용 결함 (Configuration, data or documentation content defect): 코드는 맞고, 동작을 정하는 값이나 사람에게 주는 정보의 내용(설정 값, 기본값, 정책·운영 파일, 가입자·망 데이터, 문서·절차서)이 틀렸거나 빠졌다. 제품이 제공한 값이든 운용자·사용자가 넣은 값이든 같다.
- `c.supply` 빌드·의존 구성 결함 (Build or dependency composition defect): 기능 코드가 아니라, 산출물을 빌드·패키징하는 정의나 함께 쓰는 외부 구성요소의 버전·존재·호환 조합에 원인이 있다.
- `c.test` 시험 자산 결함 (Test asset defect): 제품은 정상인데 시험 코드·시험 데이터·판정 기준·시험 구성이 틀려 시험이 실패하거나 불안정하거나 아무것도 검사하지 못했다.
- `c.operation` 운용·구축 결함 (Operation or deployment defect): 설정 값이나 구성요소 버전이 아니라, 사람이 수행한 작업 절차나 망·시스템의 구성·용량 설계에 원인이 있다. 운용자·구축 업체·사용자 누구든 같다.
- `c.env` 외부 조건·사건 (External condition or event): 결함이 있는 요소가 아니라, 제품과 운용 조직이 통제하지 않는 외부의 물리 조건·사건·공격·서비스 장애가 원인이다.

## 특수 코드

- `_none`: 원인을 판정할 내용이 원문에 없다.
- `_na`: 고칠 결함(fault)이 없어 원인을 물을 수 없는 기록이다.
- `_other`: 원인은 적혀 있지만 트리의 어느 노드에도 맞지 않는다.

## 출력

JSON 객체 하나만 낸다.

```json
{"results": [{"id": "<레코드 id>", "stop": 3, "label": "<라벨>", "evidence": "<원문 구절>"}]}
```
