# 원인 축 2단계: `c.supply` 빌드·의존 구성 결함 아래 고르기

이 레코드는 1단계에서 `c.supply`로 정해졌다. 이제 그 아래 노드 하나를 고른다.

## 할 일

1. 아래 '고르는 규칙'이 있으면 그 순서를 따른다. 없으면 정의·포함 기준이 가장 잘 맞는 노드를 고른다.
2. 더 아래 노드(세분류)가 있으면 거기까지 내려간다. 세분류를 가를 근거가 없으면 그 위 노드에서 멈춘다.
3. 하위를 가를 근거가 없으면 `c.supply` 그대로 답한다.
4. 고른 노드의 포함 기준에 맞는 구절을 레코드 원문에서 그대로 복사해 evidence에 넣는다.

완료 기준: 레코드마다 `label`이 아래 목록 안의 값이고, `evidence`가 원문에 글자 그대로 있는 구절이다.

## 하위 노드

### `c.supply.build` 빌드·패키징·CI 정의 오류 (Build, packaging or CI definition error)

- 표준 대응: ODC Target=Build/Package
- 정의: 우리 레포 안의 빌드 스크립트, 컴파일되지 않는 소스, 패키지 manifest, CI pipeline·job 정의, 산출물 저장소 운용이 틀렸다.
- 포함: 중복 const 같은 compile 오류, 폐기된 명령을 쓰는 script, package에서 빠진 파일, submodule 미반영, job의 branch·filter 누락, 지워진 cache 대상 지정, 버전 간 artifact 저장소 충돌, 경고를 오류로 다루는 설정, 빌드 옵션별 조건부 compile 경로 오류.
- 이웃과 가르기: 레포 밖 구성요소의 버전·API가 바뀌어 깨졌으면 c.supply.dependency. 특정 시험이 통과하는 데 필요한 구성(extension 활성화, 시험 환경 버전)이면 c.test.

### `c.supply.dependency` 의존 구성요소 변경·버전 부적합 (Dependency change or version mismatch)

- 표준 대응: ODC Source=Reused From Library(근사); X.733 probableCause Software Environment Problem(근사)
- 정의: 함께 쓰는 외부 구성요소(library, kernel module, toolchain, 생성기, 연동하는 외부 시스템)가 의도적으로 바뀌었거나(API·기본값·동작 변경), 선언·설치된 버전이 맞지 않거나 빠져서 동작이 달라졌다. 버전을 정한 쪽이 제품 선언이든 운용자 설치든 같다.
- 포함: 새 버전의 반환값·예외·module 경로·기본값 변경, API 폐기, 선언한 최소 버전이 낮음, 번들 library 버전 충돌, 배포판 package가 오래됨, 새 compiler가 번들 코드를 깸, 외부 도구 CLI 변화, 연동하는 외부 시스템의 새 release가 동작을 바꿈, 운용 환경에 필요한 kernel module·package가 없거나 버전이 맞지 않음, 지원 범위보다 낡은 compiler·OS package. 고친 곳이 제품 코드든 시험 코드든 여기다.
- 이웃과 가르기: 외부 구성요소 자체의 의도하지 않은 결함(upstream bug, kernel 회귀)은 c.code(원인 소재 facet=공급사·OSS). 외부 구성요소 동작은 그대로인데 우리가 잘못 썼으면 c.code.interface. 외부 저장소·mirror·서비스가 응답하지 않으면 c.env.service. 고친 방법이 버전 올림이어도 원인이 그 버전 구성요소 자체의 bug면 c.code(원인 소재 facet=공급사·OSS).

## 출력

`label`은 `c.supply`, `c.supply.build`, `c.supply.dependency` 가운데 하나다. JSON 객체 하나만 낸다.

```json
{"results": [{"id": "<레코드 id>", "label": "<라벨>", "evidence": "<원문 구절>"}]}
```
