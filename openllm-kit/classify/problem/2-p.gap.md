# 문제점 축 2단계: `p.gap` 기능·개선 필요 아래 고르기

이 레코드는 1단계에서 `p.gap`로 정해졌다. 이제 그 아래 노드 하나를 고른다.

## 할 일

1. 아래 '고르는 규칙'이 있으면 그 순서를 따른다. 없으면 정의·포함 기준이 가장 잘 맞는 노드를 고른다.
2. 더 아래 노드(세분류)가 있으면 거기까지 내려간다. 세분류를 가를 근거가 없으면 그 위 노드에서 멈춘다.
3. 하위를 가를 근거가 없으면 `p.gap` 그대로 답한다.
4. 고른 노드의 포함 기준에 맞는 구절을 레코드 원문에서 그대로 복사해 evidence에 넣는다.

완료 기준: 레코드마다 `label`이 아래 목록 안의 값이고, `evidence`가 원문에 글자 그대로 있는 구절이다.

## 하위 노드

### `p.gap.capability` 기능·지원 부재 (Missing capability)

- 표준 대응: ODC Impact Capability·Requirements
- 정의: 제품이 요구된 기능·규격 항목·구성·실행 환경·규모·관측 수단을 지원하지 않는다.
- 포함: 미구현 표준 기능, 프로토콜 버전·option 지원 요청, 미지원 topology·HW·OS·외부 library, 관리 API·CLI 동작 부재, metric·event 부재, 숨은 설정 노출 요청.
- 이웃과 가르기: 바뀐 것을 겪는 사람이 개발자·기여자뿐인 코드·시험·절차·개발 조직 정책 정리는 p.gap.maint. 있는 기능이 틀리게 동작하면 p.func.*. 이미 지원 대상인 환경에서 실행이 실패하면 p.stage.install·p.stage.startup. 속도·자원·비용 절감이 동기면 p.perf. 결함으로 올라왔다가 미지원으로 판정된 건은 관찰된 증상 노드다(판정은 resolution 축).

### `p.gap.maint` 코드·시험·절차 보강 (Maintenance or process improvement)

- 표준 대응: ODC Impact Maintenance·Migration
- 정의: 제품 사용자·운영자에게 보이는 동작은 바꾸지 않고 코드 구조·의존성·시험 범위·개발 절차를 정리하거나 보강해야 한다.
- 포함: refactor, deprecated 구성 요소 제거, 의존성·runtime upgrade·정리, style·lint 경고 정리, 빌드 체계·image 전환, 시험 추가·coverage 보강, CI·triage·보안 신고 절차 같은 개발 조직 절차 변경, 동기 없는 구현 방식 교체, 문서 사이트 이전. 시험 분할·병렬화처럼 개발 절차 시간을 줄이는 요청.
- 이웃과 가르기: 제품 사용자·운영자가 쓰는 새 동작·설정·환경 지원이 생기면 p.gap.capability. 코드가 잘못 동작할 수 있다고 지적하면 예상 증상 노드(관찰 여부 facet=예상). 시험·검사 job이 실제로 실패하면 p.stage.test. 속도·자원·비용 절감이 동기면 p.perf.

## 출력

`label`은 `p.gap`, `p.gap.capability`, `p.gap.maint` 가운데 하나다. JSON 객체 하나만 낸다.

```json
{"results": [{"id": "<레코드 id>", "label": "<라벨>", "evidence": "<원문 구절>"}]}
```
