# 문제점 축 2단계: `p.info` 문서·출력 문구 이상 아래 고르기

이 레코드는 1단계에서 `p.info`로 정해졌다. 이제 그 아래 노드 하나를 고른다.

## 할 일

1. 아래 '고르는 규칙'이 있으면 그 순서를 따른다. 없으면 정의·포함 기준이 가장 잘 맞는 노드를 고른다.
2. 더 아래 노드(세분류)가 있으면 거기까지 내려간다. 세분류를 가를 근거가 없으면 그 위 노드에서 멈춘다.
3. 하위를 가를 근거가 없으면 `p.info` 그대로 답한다.
4. 고른 노드의 포함 기준에 맞는 구절을 레코드 원문에서 그대로 복사해 evidence에 넣는다.

완료 기준: 레코드마다 `label`이 아래 목록 안의 값이고, `evidence`가 원문에 글자 그대로 있는 구절이다.

## 하위 노드

### `p.info.doc` 문서 오류·누락 (Documentation error or omission)

- 표준 대응: ODC Impact Documentation; IEEE 1044 defect Type Description(2차 출처)
- 정의: 문서, API reference, README, 예시 설정, docstring·주석이 틀리거나, 낡거나, 빠져 있다.
- 포함: 설치 명령 누락, 옵션 설명이 실제와 다름, 깨진 링크, 지원 목록 누락, 새 기능 문서화 요청(기능 요청이어도 여기), 예시 설정과 코드 불일치, 주석의 틀린 출처.
- 이웃과 가르기: 로그·경고·알람 문구는 p.info.log. 동작이 문서와 다르고 동작 쪽을 고쳐야 하면 해당 기능 노드. 문서 사이트 이전처럼 내용 결함 없는 작업은 p.gap.maint.

### `p.info.log` 로그·알람·화면 문구 이상 (Log, alarm or displayed text issue)

- 표준 대응: ODC Impact Serviceability; Avizienis detectability(false alarm·unsignaled failure)
- 정의: 실행 중 나오는 로그·경고·알람·오류 문구·화면 표시가 거짓이거나, 지나치게 많거나, 빠지거나, 수준이 맞지 않거나, 엉뚱한 원인을 가리키거나, 사용자를 헷갈리게 한다.
- 포함: 정상 상황의 오류 로그, 반복 trace, 잘못된 log level, deprecation 경고, 빌드·시험 중 불필요한 출력, 오해를 부르는 오류 문구, 값 형식이 틀린 로그, logging 호출 자체의 format 오류, 화면 단위·이름 표기 오류, 알람 누락·오탐·폭주.
- 이웃과 가르기: 문서·예시 설정은 p.info.doc. 로그가 실제로 실패한 작업을 알리면 그 실패의 노드(p.func.fail 등). 호출자가 받는 응답 코드가 틀리면 p.func.fail.

## 출력

`label`은 `p.info`, `p.info.doc`, `p.info.log` 가운데 하나다. JSON 객체 하나만 낸다.

```json
{"results": [{"id": "<레코드 id>", "label": "<라벨>", "evidence": "<원문 구절>"}]}
```
