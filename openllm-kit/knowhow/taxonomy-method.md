# 분류 체계 넓히기·고치기

새 문서 종류(알람, 고객 티켓, 장애 보고서, 시험 리포트, CVE 등)가 들어오거나 라벨이 자주 엇갈릴 때, 분류 체계(`taxonomy/*.json`)를 바꾸는 절차다. 분류 체계는 문제점·원인·해결책 세 축의 트리이고, 각 축은 질문 하나로 가른다.

## 할 일

1. **엇갈림 표본을 따로 둔다.** 고칠 때 읽는 개정 표본과, 판정에만 쓰는 held-out 표본을 나눈다. held-out 레코드는 읽지 않고 examples에도 넣지 않는다. 완료 기준: 두 표본의 case_code 목록이 파일로 있고 서로 겹치지 않는다.
2. **현재 판으로 두 번 단다.** 개정 표본을 같은 모델·같은 절차로, 레코드 순서와 묶음만 바꿔 두 번 단다. 완료 기준: 축마다 L1·잎 일치율과 kappa, 엇갈린 레코드 목록이 있다.
3. **엇갈림을 모두 읽고 원인별로 묶는다.** 일부만 읽지 않는다. 완료 기준: 엇갈린 레코드마다 원인 묶음 하나가 붙었다. 원인 묶음은 아래 #엇갈림 원인 표의 이름을 쓴다.
4. **판정 기준을 고친다.** 경계 문장을 늘리기 전에 아래 #고치는 순서를 따른다. 특정 레코드를 위한 예외 규칙은 넣지 않는다. 완료 기준: 바꾼 것마다 '어느 엇갈림 묶음을 겨냥했나'가 `changes_from_*`에 적혔다.
5. **held-out으로 판정한다.** 새 판과 이전 판을 held-out에서 같은 방식으로 두 번씩 달고, 같은 레코드끼리 짝지은 paired bootstrap 95% 구간을 낸다. 완료 기준: 구간 하한이 0 위인 지표가 있으면 채택한다. 개정 표본에서만 오르면 채택하지 않는다.

## 구조 규칙

| 규칙 | 내용 |
|---|---|
| 축 독립 | 한 축의 판정에 다른 축 값을 쓰지 않는다. '결함 아님' 처분은 해결책 축에만 있다 |
| facet | 어디서(장비군·NF·프로토콜·제품·버전·모듈), 누구 것(자사·공급사·운용자·제3자), 확신 정도(명시·추론), 무엇을 바꿨나(코드·설정·시험·문서·HW)는 트리 밖 속성이다 |
| 깊이 | 축 루트 아래 최대 3단. L1은 축마다 4~9개, 한 노드의 자식은 2~9개 |
| L1·L2 여는 근거 | 표준 범주(ODC, IEEE 1044, X.733 등)가 받치거나, 문서 종류 둘 이상에서 따로 판정된다. 현재 데이터 빈도만으로는 열지 않는다 |
| L3 여는 근거 | 자식마다 판정 가능 표의 2% 이상이고, held-out에서 같은 L2 안 L3 일치가 0.9 이상이다. 표준 값과 1:1이면 2% 조건은 면제다 |
| 특수 코드 | `_none` 정보 없음, `_na` 해당 없음(결함이 없는 기록), `_other` 맞는 노드 없음. 트리 밖에 둔다 |
| 중간 노드 | 하위를 가를 근거가 없으면 중간 노드에 단다. 중간 노드 배정이 2%를 넘으면 자식 개설 후보다 |
| 원천 하나 | 정의는 `taxonomy/*.json` 한 곳에만 둔다. 절차서·키워드 사전은 `openllm-kit/tools/build.py`로 생성한다 |

## 엇갈림 원인

엇갈림은 대개 아래 넷 가운데 하나다.

| 이름 | 모양 | 고치는 곳 |
|---|---|---|
| 기준 섞임 | 형제 노드가 서로 다른 질문(값의 출처, 객체 수명, 상대 계약 등)으로 나뉘어 한 레코드가 둘에 맞는다 | 그 층의 판정 기준을 하나로 정하고, 둘 이상 맞을 때의 우선순위를 적는다 |
| 축 섞임 | 확신 정도·처분·위치처럼 다른 축이나 facet의 값이 노드 조건에 들어 있다 | 그 조건을 facet이나 다른 축으로 옮긴다 |
| 정의 모순 | 두 노드의 정의가 서로를 가리킨다 | 상위(루트·L1)에 우선순위를 적어 한쪽으로 보낸다 |
| 규칙 놓침 | 규칙은 있는데 라벨러가 놓친다 | 코드로 정할 수 있으면 코드로 옮긴다(예: 레코드 유형이 기능 요청이면 원인 `_na`) |

## 고치는 순서

1. 코드로 정할 수 있는 판정은 코드로 옮긴다.
2. 다른 축·facet의 값이 섞였으면 옮긴다.
3. 한 층의 기준이 섞였으면 기준 하나와 우선순위를 정한다. 원인 축 소프트웨어 결함 하위는 '고친 내용'(IBM ODC Defect Type 방식)이 기준이다.
4. 그래도 남는 경계만 정의·포함·제외 문장으로 가른다.
5. 노드를 합치거나 나누는 것은 위가 다 끝난 뒤, #구조 규칙의 근거가 있을 때만 한다.

## 이 체계가 지나온 판

| 판 | 바꾼 것 | 결과(held-out, 같은 Haiku 두 pass) |
|---|---|---|
| v1→v2 | 귀납 3개를 합친 판에서 혼동·작은 잎을 정리 | cause L1 kappa 0.897→0.938 |
| v2→v3 | 축 섞임 세 곳 제거, 새 문서 종류용 노드(설비 상태, HW, 절차 조치) 개설 | problem 0.906→0.936, resolution 0.943→0.951, cause 0.938→0.915 |
| v3→v4(cause) | 기준 섞임(c.code L2)을 '고친 내용'과 우선순위로, 축 섞임(확신 정도)을 facet으로, 정의 모순을 L1 우선순위로 | cause 0.915→0.955, L1 일치 +2.9%p [+0.2, +5.6] |

근거와 표는 `docs/design/04-taxonomy.md`에 있다.
