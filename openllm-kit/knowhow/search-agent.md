# 결함 검색 에이전트 구조

네트워크 부서용 결함 검색 에이전트를 만들거나 바꿀 때 지키는 구조 규칙이다. 근거는 공개 이슈 10,000건 대체 데이터셋의 시뮬레이션(test 117문항, BM25·hybrid·rerank 세 검색 모드)이다. 수치와 표는 `docs/design/01~03`에 있다.

## 남길 칸

검색 단계를 BM25 → hybrid(BM25+dense) → rerank로 바꿔도 아래 칸은 모두 필요했다. 이 칸들은 데이터가 바뀌어도 유지한다.

| 칸 | 하는 일 | 끄면 |
|---|---|---|
| 식별자 경로 | 로그 문구·함수명·파일 경로를 역색인에서 정확히 찾는다 | 로그 붙여넣기 질문 성공률 1.000→0.611(rerank) |
| 관계 확장 | 원인이 추론·미상인 상위 결과에서 중복·xref로 이어진, 원인이 명시된 레코드를 끌어온다 | 원인 이어받기 질문 1.000→0.444(rerank) |
| 검색 점수 기반 기권 | 검색 단계가 낸 점수(reranker 점수가 가장 잘 갈랐다)가 기준보다 낮고 식별자 일치가 없으면 "유사 사례 없음"으로 답한다 | BM25 점수로 했을 때 답이 있는 문항의 17%를 막았다 |
| 수정 추적 | 수정 상태를 `fixed_in_version / not_backported / wont_fix / fix_ref_only / workaround_only / unknown`으로 낸다. "고쳐졌지만 참조·버전 없음"을 더할 후보로 둔다 | 버전을 모르는데 아는 척하는 답이 생긴다 |
| 집계 | 정해진 template에 파라미터만 채운다. 원인 미상 레코드 수를 답에 함께 적는다 | 자유 SQL은 쓰지 않는다 |

## 계획을 세우는 쪽

- **고정 경로가 기본이다.** 코드가 질문의 slot·의도에서 실행 경로(DAG)를 정한다. LLM 호출 없이 단일 LLM 도구 루프·LLM planner와 성공률이 같았다(rerank: 0.863 / 0.812 / 0.872, 차이 구간 모두 0 포함).
- **LLM은 앞단 한 번에 쓴다.** 검색어 재작성과 범위 판단(데이터에 있을 법한 질문인가)을 한 호출로 맡긴다. 이 둘이 루프가 앞섰던 이유였고, 검색에 reranker가 붙으면 이득이 줄었다.
- **배타 경로는 코드가 다시 확인한다.** 집계처럼 다른 단계를 건너뛰는 경로는 LLM 의도 라벨 하나로 열지 않는다. 질문에 건수 낱말이 실제로 있을 때만 연다. 전처리 첫 판은 "로그가 반복된다"를 건수 질문으로 읽어 성공률이 0.581로 떨어졌다.
- **LLM planner는 결과를 보지 못한다.** 그래서 쓸데없는 단계를 넣는다. 고정 경로가 모자란 질문이 로그로 쌓일 때 다시 본다.

## 되묻기

- **답을 먼저 주고 끝에 한 줄로 묻는다.** 제품·장비군처럼 결과를 갈라놓는 범주형 slot만 묻는다. 막고 묻으면 최종 성적은 같은데 첫 응답만 비었다.
- **받은 값은 soft로 반영한다.** 사용자가 준 값으로 결과를 걸러 내면, 틀린 값을 받았을 때 Hit@5가 0.92→0.72(rerank)로 떨어졌다. 점수 가중으로 쓰면 0.92를 지켰다.
- **채울 수 있는 값은 묻지 않는다.** 앞 턴, 사용자 프로필(담당 제품), 첨부에서 먼저 채운다. 같은 slot은 대화에서 한 번만 묻고, 횟수는 코드가 센다.
- **검색이 좋아지면 물을 일이 준다.** 묻는 비율이 BM25 46% → rerank 20%로 줄었다. 묻는 조건(상위 결과의 제품 쏠림 기준)은 데이터마다 다시 잰다.

## 데이터 쪽

- 정의·어휘는 SKOS 모양 통제 어휘(`taxonomy/*.json`)를 원천으로 둔다. OWL 정식 온톨로지는 ID 체계가 셋 이상 겹치거나 외부와 표준 모델로 데이터를 주고받을 때 다시 본다.
- 그래프는 명시 관계(중복, 같은 저장소 이슈 참조, 같은 수정)만 edge로 둔다. 에러 문구·함수·파일 공유는 edge로 펼치지 않고 질의할 때 역색인으로 찾는다.
- 원인 이어받기는 중복·xref 경로로만 한다. 같은 수정을 공유한 쌍은 원인 분류가 같은 비율이 절반 아래였다.
